Web fundamentals

HTTP Request Lifecycle

A browser turns a URL into a rendered page through name resolution, connection setup, a request-response exchange, and rendering.

Mental model

Think of the browser as a client sending a precisely addressed order. DNS finds the destination, the network establishes a route, the server prepares a response, and the browser assembles the result.

Step by step

1. Read the URL

The browser separates the URL into its scheme, hostname, optional port, path, query parameters, and fragment. The scheme tells it whether the request normally uses HTTP or HTTPS.

2. Find the server

The browser needs an IP address for the hostname. It checks local caches first. If no useful result exists, a DNS resolver follows the DNS hierarchy and returns an address.

3. Establish a connection

The browser opens a transport connection. HTTP/1.1 and HTTP/2 commonly use TCP. HTTP/3 uses QUIC over UDP. HTTPS also requires a secure TLS session so the browser can verify the server and encrypt traffic.

4. Send the HTTP request

The request contains a method such as GET or POST, a path, headers, and sometimes a body. Headers communicate details such as accepted formats, cookies, caching information, and the browser identity.

5. Process the request

A web server, reverse proxy, application, cache, and database may all participate. The exact path depends on the system, but the result is an HTTP response.

6. Receive the response

The response contains a status code, headers, and usually a body. A status such as 200 indicates success, 301 or 302 redirects the browser, 404 means the resource was not found, and 500 indicates a server failure.

7. Render the page

The browser parses HTML into a document tree, fetches referenced resources, applies CSS, runs JavaScript, calculates layout, and paints pixels. A single page can therefore trigger many additional requests.

Supporting layers

Layer Purpose Typical result
DNS Find the network address for a hostname An IPv4 or IPv6 address
TCP or QUIC Transport data between browser and server A usable connection
TLS Authenticate and encrypt an HTTPS connection A secure session
HTTP Define request and response messages Status, headers, and content
Browser rendering Turn resources into an interactive page Pixels and behavior

Caching and repeated visits

Not every visit repeats every step. DNS answers can be cached, transport connections can be reused, TLS sessions can resume, and HTTP responses can be served from a browser or intermediary cache. These shortcuts improve speed, but every cache needs rules for freshness and invalidation.

Common misunderstandings

  • HTTP is the message protocol; it is not the same thing as DNS, TCP, QUIC, or TLS.
  • Loading one page normally creates many requests for styles, scripts, images, fonts, and data.
  • The server can represent several components rather than one physical machine.
  • A successful network connection does not guarantee a successful HTTP response.
  • Caching may skip work, so two visits to the same URL can follow different paths.
